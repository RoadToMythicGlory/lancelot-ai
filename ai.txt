1. OVERVIEW & IDENTITY
================================================================================

The Lancelot AI Agent is a local LLM-powered assistant designed as a "digital 
employee" within the Lancelot ERP broadcast system. Unlike typical chatbots, 
it is integrated into the existing chat system as a first-class user participant.

KEY CHARACTERISTICS:
- Identity Email: lancelot-ai@internal.system
- Display Name: Lancelot AI (לנסלוט)
- User Type: AI Agent (isAIAgent: true flag in database)
- Language Support: Hebrew (primary) and English
- Offline-First: All inference runs locally via Ollama
- No Cloud Dependencies: Never makes external LLM API calls
- Operational Mode: Reliability-first with hard gates and anti-hallucination

DESIGN PHILOSOPHY:
The agent is NOT a separate UI component or chatbot interface. It participates 
in the platform's existing Socket.IO-based chat system just like a human user:
- Has its own user account in MongoDB
- Receives messages via chat routing
- Sends responses through the same chat infrastructure
- Can participate in E2EE conversations (owns cryptographic keys)

RELIABILITY PRINCIPLES (Feb 2026 Hardening):
The agent behaves like a reliable broadcast operator, not a "smart chatbot":
- Operational intents (cg, lineup, shifts, news, rights) NEVER produce free chat
- Missing data → clarification questions, NEVER invented facts
- Tool execution required → no hallucinated substitutes
- Source-only policy → news/items must come from verified RSS feeds or be labeled placeholder
- LIVE CG mode → deterministic parsing with Viz validation, no LLM guessing

The AI Agent provides six primary tool categories:

1. CHAT INTERFACE (General Conversation)
   - Natural language understanding (Hebrew + English)
   - Context-aware responses
   - Greeting detection (hardcoded responses)
   - Conversation history tracking
   
2. LINEUP BUILDER
   Intent: "lineup"
   Purpose: Generate program rundowns for sports, news, entertainment
   Features:
   - Dual modes: STRUCTURE (segment-based) vs ITEMS (content-based)
   - Structure mode: traditional segment flow (intro/interview/break)
   - Items mode: fetches real articles from RSS, fills N items by category
   - Exact count enforcement: respects totalItems and categoryCounts
   - Source-only policy: never invents fake news headlines
   - Real articles with citations OR placeholder skeletons
   - Category-based article matching with exclusion rules
   Schema: services/ai-agent/src/schemas/lineup-rundown.ts
   New schemas: ItemsLineup, LineupItem, LineupTypeSchema
   
3. CG ASSISTANT (Graphics Specifications)
   Intent: "cg"
   Purpose: Create structured graphics specifications for Vizrt
   Features:
   - Lower third specs
   - Scorebug configurations
   - Ticker layouts
   - LIVE CG mode: deterministic regex parsing (near-zero error)
   - Validates against Viz constraints (40 char max for names, RTL normalization)
   - Returns JSON-only in LIVE mode with requiresApproval flag
   - Detects mode via context.metadata.mode = "LIVE_CG" or message prefix
   Schema: services/ai-agent/src/schemas/cg-spec.ts
   New functions: parseLiveCGMessage(), isLiveCGRequest(), validateCGTextField()
   
4. SHIFT SCHEDULER
   Intent: "shifts"
   Purpose: Intelligent shift scheduling assistance
   Features:
   - Constraint extraction mode: LLM extracts requirements, never invents schedule
   - Availability analysis
   - Swap recommendations
   - Constraint solving with greedy algorithm (OR-Tools integration ready)
   - Returns extracted constraints + missing info when data incomplete
   Note: LLM = constraint extractor; solver = scheduling logic
   Schema: services/ai-agent/src/schemas/shift-schedule.ts
   New functions: extractShiftConstraints()
   
5. NEWS FETCHER
   Intent: "news"
   Purpose: RSS-based news aggregation from trusted sources
   Features:
   - Multi-source RSS parsing
   - Caching for offline mode (24h TTL)
   - Trusted source allowlist
   - Article deduplication by excerptHash
   - Truth boundary enforcement: no sources → explicit message, never invention
   - Returns source citations with confidence scores
   - Integrated with items lineup for real article population
   File: services/ai-agent/src/tools/news-fetcher.ts
   Config: services/ai-agent/src/config/trusted-sources.ts
   Cache: services/ai-agent/src/data/news-cache.ts
   
6. RIGHTS BOARD
   Intent: "rights"
   Purpose: Broadcast rights and sports intelligence tracking
   Features:
   - Sports fixtures tracking
   - League information
   - Broadcast rights status
   Schema: services/ai-agent/src/schemas/rights-board.ts

TOOL EXECUTION FLOW:
services/ai-agent/src/agent/orchestrator.ts

2. Check if clarification needed
3. Look up tool handler in registry

4b. RELIABILITY HARDENING (February 2026)
================================================================================

PROBLEM STATEMENT:
Original agent behavior had critical reliability issues for live broadcast ops:
- Agent "talked" instead of executing tools for operational requests
- Confidently hallucinated: invented facts, dates, scores, rights info
- Misinterpreted rundown requests (returned generic skeletons vs specific items)
- For LIVE CG, LLM-only behavior was too error-prone
- Shift scheduling attempted with LLM logic instead of constraint solver
- News writing crossed truth boundaries and invented content

SOLUTION - OPERATIONAL HARD GATES:
Files: orchestrator.ts, intent-classifier.ts, all tool handlers

Key Functions:
- isOperationalIntent(intent): Returns true for cg/lineup/shifts/news/rights
- requiredEntitiesSatisfied(intent, entities, message): Validates required data
- buildMissingEntitiesClarification(intent, missing): Asks for missing info

Behavior:
Operational intents follow: TOOL → OR → CLARIFICATION → OR → EXPLICIT ERROR
They NEVER fall through to free-form LLM chat.

Gate Logic in processMessage():
1. After intent classification, check if operational
2. If operational AND entities missing → clarification response
3. If operational AND tool not registered → explicit error
4. If operational AND tool fails → explicit failure message
5. Safety net: free chat path blocked with error if operational intent reaches it

LINEUP: ITEMS vs STRUCTURE DETECTION:
Problem: User asked for "12 items with category counts", got generic segment skeleton.

Solution:
- New entity: lineupType = "items" | "structure"
- Detection rules:
  * Numbers + categories ("12 פריטים", "5 כדורגל") → items
  * Segments/flow words ("פתיח", "ראיון", "הפסקה") → structure
- Functions: detectLineupType(), extractItemCount(), extractCategoryCounts()

Items Mode Behavior:
- Fetches real articles from RSS sources
- Scores articles for category relevance with mustMatch/excludeMatch rules
- Assigns articles to categories (deduplication across categories)
- Fills with real headlines + source citations
- Placeholders ONLY where no matching articles found
- NEVER invents fake news

Structure Mode Behavior (unchanged):
- Traditional segment-based templates (intro/interview/break)
- Time allocation and scaling
- Breaking news incorporation

LIVE CG MODE:
Problem: LIVE ops require near-zero error; LLM-only is too unpredictable.

Solution:
- Deterministic regex parsing for scorebug/lower third/slate
- Extracts: teams, scores, times, names, titles
- Validates against Viz constraints: 40 char max, RTL normalization, no control chars
- Returns: { parseSuccess, templateType, fields, missing, validationErrors }
- LLM extraction only as fallback when deterministic parsing incomplete
- Output: JSON-only with requiresApproval=true flag (no free text)

Detection:
- context.metadata.mode = "LIVE_CG"
- OR message prefix: "CG LIVE", "LIVE_CG"

Functions:
- parseLiveCGMessage(message): Deterministic field extraction
- isLiveCGRequest(message, mode): Mode detection
- validateCGTextField(value, maxLen): Viz constraint validation
- normalizeRTL(text): Hebrew text normalization

ANTI-HALLUCINATION ENFORCEMENT:
System Prompt Updates (AGENT_SYSTEM_PROMPT):
- "Never guess. If info missing, say you don't have data and ask 1-2 questions."
- "Never invent facts, dates, scores, rights, or names."
- "Never produce content that looks factual without verified source."
- "For operational tasks: execute tool or ask clarification. Never free-form text."
- "If tool fails, report failure clearly. Never invent substitute result."

Backed by code gates:
- Operational hard gates in orchestrator
- Source-only policy in news/lineup tools
- Explicit placeholder labeling when data unavailable

JSON VALIDATION WITH REPAIR LOOP:
Function: enforceStructuredOutput<T>(rawOutput, schema, repairFn)

Flow:
1. Parse LLM output with Zod schema
2. If valid → return data
3. If invalid → call repairFn ONCE with error description
4. Parse repaired output
5. If still invalid → return explicit error with details
6. NEVER accept partial or hallucinated data

Used in: CG field extraction, lineup enhancements, any tool expecting JSON

SHIFT SCHEDULING - CONSTRAINT EXTRACTION:
Function: extractShiftConstraints(message)

Behavior:
- LLM extracts scheduling constraints from natural language
- Returns: { department, weekStartDate, roles, hardConstraints, availabilityNotes, missingConstraints }
- If critical data missing → returns what was extracted + questions for user
- NEVER generates a schedule without solver
- LLM role = interface + explanation; solver = optimization

NEWS TRUTH BOUNDARY:
- No RSS articles available → explicit message: "לא נמצאו חדשות ממקורות מאומתים"
- Offers alternatives: provide bullet points OR check RSS config OR retry later
- Writing requires sources/notes; no invention
- All news items include source attribution: [sourceName]

5. RSS PIPELINE SYSTEM (NEW - February 2026)
================================================================================

OVERVIEW:
A comprehensive RSS ingestion and processing system that provides production-grade
news and sports content aggregation. The pipeline replaces ad-hoc RSS fetching with
a structured, cacheable, and highly reliable workflow.

KEY GOALS:
- Production-ready RSS ingestion from trusted sources
- Deduplicated article storage with MongoDB TTL
- Category-aware ranking and selection
- LLM-generated briefs for selected articles
- Graceful degradation (per-feed errors don't stop pipeline)
- Offline support via cached articles
- Feed verification tooling

ARCHITECTURE:
The RSS pipeline is a 7-stage orchestrated workflow:

┌─────────────────────────────────────────────────────────────────────────┐
│                         RSS PIPELINE FLOW                                │
│                                                                           │
│  1. Get Active Feeds (rss-config.ts)                                     │
│     → Filters feeds with active=true AND url≠'<TODO_VERIFY>'            │
│                                                                           │
│  2. Fetch All Active Feeds (rss-client.ts)                               │
│     → Concurrent fetch with timeout                                      │
│     → XML parsing via fast-xml-parser                                    │
│     → Per-feed error isolation                                           │
│                                                                           │
│  3. Dedup + Store (rss-dedup.ts + rss-articles-store.ts)                │
│     → Hash-based deduplication (title, excerpt, URL)                     │
│     → Store to rssArticles collection with TTL                           │
│                                                                           │
│  4. Retrieve Pool (rss-articles-store.ts)                                │
│     → Query by time window (default 24h)                                 │
│     → Category filtering (optional)                                      │
│                                                                           │
│  5. Rank Pool (rss-ranking.ts)                                           │
│     → Score articles per requested category                              │
│     → mustMatch / boostMatch / excludeMatch rules                        │
│     → Sort by relevance                                                  │
│                                                                           │
│  6. Select for Lineup (rss-selection.ts)                                 │
│     → Exact count fulfillment per category                               │
│     → Greedy allocation (best score first)                               │
│     → Fill with placeholders when insufficient articles                  │
│                                                                           │
│  7. Generate Briefs (rss-brief-generator.ts)                             │
│     → LLM-generated summaries for REAL articles only                     │
│     → Placeholders bypass brief generation                               │
│     → Output: briefText, bullets, whyItMatters, citation                 │
│                                                                           │
└─────────────────────────────────────────────────────────────────────────┘

MODULE BREAKDOWN:

1. RSS CONFIG (src/rss/rss-config.ts)
   Purpose: Central configuration for pipeline and feed sources
   
   Key exports:
   - rssPipelineConfig: Global settings (TTL, timeout, window, etc.)
   - rssFeedSources: Array of feed definitions
   - getActiveFeeds(sourceIds?, warnings?): Filter active/verified feeds
   
   Feed definition:
   {
     id: 'one_sports',
     name: 'ONE',
     url: 'https://www.one.co.il/cat/news/rss',
     lang: 'he' | 'en',
     categories: ['ספורט ישראלי'],
     priority: 85,  // 0-100 score for source ranking
     active: true,  // Must be true for feed to run
     type: 'rss',
   }
   
   Current active feeds:
   - one_sports (ONE - Israeli sports)
   - ynet_sports (Ynet Sports)
   - espn_sports (ESPN)
   
   Environment variables:
   - RSS_PIPELINE_ENABLED (default: false)
   - RSS_DEBUG_RANKING (default: false)
   - RSS_CACHE_TTL_MINUTES (default: 60)
   - RSS_FETCH_TIMEOUT_MS (default: 10000)
   - RSS_TIME_WINDOW_HOURS (default: 24)

2. RSS CLIENT (src/rss/rss-client.ts)
   Purpose: Fetch and parse RSS/Atom feeds
   
   Key functions:
   - fetchActiveFeeds(feeds): Fetch all feeds concurrently
   - fetchFeed(feed): Fetch single feed with timeout
   - parseRssFeed(xml, feedConfig): Parse XML to ArticleCandidate[]
   
   Features:
   - Supports RSS 2.0, Atom, RDF
   - fast-xml-parser for robust XML parsing
   - Per-feed error isolation (one failure doesn't stop others)
   - Timeout protection (10s default)
   - Concurrent fetch with limit (5 feeds at a time)
   
   XML Parser config:
   - Handles CDATA sections
   - Extracts: title, link, description, pubDate, category, author
   - Attribute handling: @_ prefix
   - Array coercion for <item> and <entry> tags

3. RSS DEDUP (src/rss/rss-dedup.ts)
   Purpose: Hash-based deduplication of articles
   
   Key functions:
   - deduplicateArticles(articles): Remove exact duplicates
   - computeArticleHashes(article): Generate title/excerpt/URL hashes
   
   Hashing strategy:
   - titleHash: SHA-256 of normalized title
   - excerptHash: SHA-256 of first 500 chars of summary
   - urlHash: SHA-256 of URL
   - Compound ID: source + ':' + urlHash
   
   Normalization:
   - Lowercase
   - Strip HTML tags
   - Remove extra whitespace
   - Trim

4. RSS ARTICLES STORE (src/data/rss-articles-store.ts)
   Purpose: Dedicated MongoDB storage for RSS articles
   
   Collection: rssArticles
   _id: source:urlHash (compound identifier)
   TTL: expiresAt field with expireAfterSeconds: 0
   
   Key functions:
   - initializeRssArticlesStore(): Create indexes
   - storeArticle(candidate): Store single article
   - storeArticles(candidates): Bulk store with duplicate handling
   - getArticlesByTimeWindow(hours, categories?, limit?): Query articles
   - getArticleById(id): Direct lookup
   - getRssStoreStats(): Collection statistics
   
   Indexes:
   - { expiresAt: 1 } with expireAfterSeconds: 0 (TTL)
   - { titleHash: 1, excerptHash: 1 } (dedup diagnostics)
   - { fetchedAt: -1 } (time-window queries)
   - { publishedAt: -1 } (recency ranking)
   - { source: 1 } (per-feed queries)
   - { rawCategories: 1 } (category filtering)
   
   Document schema:
   {
     _id: string,               // source:urlHash
     url: string,
     source: string,            // Feed ID
     sourceName: string,        // Display name
     title: string,
     summary: string,
     publishedAt: Date,
     publishedAtEstimated: boolean,
     fetchedAt: Date,
     lang: 'he' | 'en',
     rawCategories: string[],   // Feed-provided categories
     contentLevel: 'rss_only',
     excerptHash: string,
     titleHash: string,
     urlHash: string,
     expiresAt: Date,           // TTL expiration
   }

5. RSS RANKING (src/rss/rss-ranking.ts)
   Purpose: Score articles for category relevance
   
   Key functions:
   - rankPool(articles, categoryCounts): Rank all articles per category
   - scoreArticleForCategory(article, category): Individual scoring
   
   Ranking strategy:
   - Each category has mustMatch / boostMatch / excludeMatch rules
   - mustMatch: Required patterns (hard filter)
   - boostMatch: Relevance boosters (soft ranking)
   - excludeMatch: Rejection patterns (hard filter)
   
   Scoring:
   - Base score: 50
   - mustMatch hit: continue scoring
   - mustMatch miss: score = 0 (reject)
   - boostMatch hit: +20 per pattern
   - excludeMatch hit: score = 0 (reject)
   - Source priority: +0 to +30 (based on feed config)
   - Recency: +0 to +20 (newer articles ranked higher)
   - Language match: +10 (if requested lang matches article)
   
   Category rules example (כדורגל ישראלי):
   - mustMatch: Israeli team names OR Israeli league keywords
   - excludeMatch: Premier League, La Liga, Champions League
   - boostMatch: Maccabi, Hapoel, Ligat Ha'al
   
   Output: RankedArticle[]
   {
     articleId: string,
     category: string,
     score: number,
     reasons: string[],  // Human-readable scoring explanation
     reject: boolean,
   }

6. RSS SELECTION (src/rss/rss-selection.ts)
   Purpose: Select exact article counts per category
   
   Key functions:
   - selectForLineup(rankedPool, candidateMap, totalItems, categoryCounts)
   
   Selection strategy:
   - Per-category allocation (exact counts)
   - Greedy selection (best score first within category)
   - No duplicates across categories
   - Fill remaining slots with placeholders
   
   Output: SelectedArticle[]
   {
     article: ArticleCandidate,  // Real article or placeholder
     isPlaceholder: boolean,
     category: string,
     score: number,
   }
   
   Placeholder schema:
   {
     id: 'placeholder-<uuid>',
     title: '[Placeholder: <category>]',
     summary: 'No matching articles found for this category.',
     isPlaceholder: true,
     // ... other required fields with empty/default values
   }

7. RSS BRIEF GENERATOR (src/rss/rss-brief-generator.ts)
   Purpose: Generate LLM-powered summaries for articles
   
   Key functions:
   - generateBriefs(articles): Batch generate briefs
   - generateSingleBrief(article): Single article brief
   
   LLM prompt:
   - Input: article.title + article.summary
   - Output: { briefText, bullets[], whyItMatters }
   - Model: qwen2.5:7b (Hebrew support)
   - Timeout: 30s
   
   Brief schema:
   {
     articleId: string,
     briefText: string,         // 2-3 sentence summary
     bullets: string[],         // 3-5 key points
     whyItMatters: string,      // Why this is important
     briefQuality: 'llm' | 'rss_only',
     citation: {
       source: string,
       url: string,
       publishedAt: string,
     },
   }
   
   Fallback strategy:
   - If LLM unavailable → briefQuality: 'rss_only', use raw summary
   - If LLM fails → log error, skip brief (graceful degradation)
   - Placeholders NEVER get briefs

8. RSS PIPELINE ORCHESTRATOR (src/rss/rss-pipeline.ts)
   Purpose: Execute full 7-stage pipeline
   
   Key function:
   - runRssPipeline(options): Full pipeline execution
   
   Options:
   {
     categoryCounts: Record<string, number>,  // e.g. { "כדורגל ישראלי": 5 }
     totalItems: number,                      // Total articles needed
     timeWindowHours?: number,                // Default: 24
     sources?: string[],                      // Filter by feed IDs
   }
   
   Output: RSSPipelineResult
   {
     items: ArticleCandidate[],    // Selected articles (real + placeholders)
     briefs: Brief[],               // LLM-generated briefs (real articles only)
     errors: FeedError[],           // Per-feed errors
     stats: {
       feedsFetched: number,
       feedsFailed: number,
       articlesIngested: number,
       duplicatesSkipped: number,
     },
   }
   
   Graceful degradation:
   - Per-feed errors logged, pipeline continues
   - Zero active feeds → explicit error, empty result
   - Store failure → use cached articles
   - No articles in pool → placeholders fill lineup
   - Brief generation failure → skip brief, article still included

9. RSS SCHEMAS (src/schemas/rss-schemas.ts)
   Purpose: Zod validation schemas for RSS types
   
   Schemas:
   - ArticleCandidateSchema
   - BriefSchema
   - BriefQualitySchema ('llm' | 'rss_only')
   - BriefCitationSchema
   - RankedArticleSchema

SCRIPTS:

1. RSS FEED VERIFICATION (src/scripts/verify-rss-feeds.ts)
   CLI: npm run rss:verify
   
   Purpose: Verify feed health before activation
   
   Checks per feed:
   0. SKIP if url === '<TODO_VERIFY>'
   1. FAIL if domain not in allowlist (terminal)
   2. HTTP GET + latency measurement (15s timeout)
   3. XML validity check
   4. Minimum item count (≥3 with title + link)
   5. Date field check (≥70% with pubDate/updated → WARN if below)
   6. Latency report
   
   Does NOT:
   - Auto-activate feeds (manual activation required)
   - Check RSS_PIPELINE_ENABLED flag (runs regardless)
   
   Output:
   - [PASS] feed_id (name) - N items, XXXms, N/N have pubDate
   - [WARN] feed_id (name) - N items, XXXms, N/N have pubDate (XX%)
   - [FAIL] feed_id (name) - reason, XXXms
   - [SKIP] feed_id (name) - URL not configured
   
   Exit code: 1 if any feeds failed

INTEGRATION WITH LINEUP BUILDER:

File: src/tools/lineup-builder.ts

When lineupType = 'items':
1. Extract totalItems and categoryCounts from user request
2. Call runRssPipeline({ categoryCounts, totalItems, timeWindowHours: 24 })
3. Receive items[] + briefs[]
4. Map to LineupItem[] schema:
   {
     id: string,
     title: string,
     summary: string,        // From brief.briefText OR article.summary
     bullets: string[],      // From brief.bullets OR []
     whyItMatters: string,   // From brief.whyItMatters OR ''
     category: string,
     duration: number,       // Estimated from content length
     isPlaceholder: boolean,
     source: string,
     url: string,
     publishedAt: string,
   }

When lineupType = 'structure':
- Traditional segment-based generation (unchanged)
- Does NOT use RSS pipeline

MONGODB COLLECTIONS:

rssArticles:
- Purpose: Persistent cache for RSS pipeline
- TTL: Configurable (default 60 min)
- Indexes: See "RSS Articles Store" above
- Independent from fetchedArticles (news-cache.ts)

fetchedArticles (legacy):
- Purpose: Old news cache (still used by news-fetcher.ts)
- Status: Coexists with rssArticles (no conflict)
- Future: May be deprecated in favor of RSS pipeline

PERFORMANCE:

Typical execution times:
- Feed fetch: 1-5s per feed (concurrent)
- Dedup + store: 100-500ms (bulk insert)
- Pool retrieval: 50-200ms (indexed query)
- Ranking: 10-50ms (in-memory scoring)
- Selection: 5-20ms (greedy allocation)

Total pipeline: 5-15s for 5-10 articles (depends on LLM and feed count)

- MongoDB TTL: 60 min (configurable)

PIPELINE STAGES (Updated Feb 2026 - Reliability Hardening):

┌─────────────────────────────────────────────────────────────┐
│ STAGE 1: LLM AVAILABILITY CHECK                              │
│ - Check if Ollama is running                                 │
│ - Return error if unavailable                                │
└──────────────────┬───────────────────────────────────────────┘
                   ▼
┌─────────────────────────────────────────────────────────────┐
│ STAGE 2: GREETING DETECTION (BYPASS)                         │
│ - Pattern match: "שלום", "היי", "hello", "hi"              │
│ - Return hardcoded greeting response                         │
│ - Skip LLM if greeting detected                              │
└──────────────────┬───────────────────────────────────────────┘
                   ▼
┌─────────────────────────────────────────────────────────────┐
│ STAGE 3: INTENT CLASSIFICATION                               │
│ - Quick classify (keyword patterns) OR LLM classify          │
│ - Extract entities (dates, names, teams, lineupType, etc.)  │
│ - Return: { primary, confidence, entities }                 │
└──────────────────┬───────────────────────────────────────────┘
                   ▼
┌─────────────────────────────────────────────────────────────┐
│ STAGE 3b: LOW-CONFIDENCE CLARIFICATION CHECK                 │
│ - If confidence < 0.4 or intent = "clarification"           │
│ - Generate clarification question                            │
│ - Return without tool execution                              │
└──────────────────┬───────────────────────────────────────────┘
                   ▼
┌─────────────────────────────────────────────────────────────┐
│ STAGE 3c: OPERATIONAL HARD GATE (NEW)                        │
│ - If isOperationalIntent(cg/lineup/shifts/news/rights)      │
│   → Check requiredEntitiesSatisfied()                       │
│   → If missing entities: buildClarification() and STOP      │
│   → If tool not registered: return error and STOP           │
│   → BLOCK free chat fallback for operational intents        │
│ - If intent = "general": allow free chat path               │
└──────────────────┬───────────────────────────────────────────┘
                   ▼
┌─────────────────────────────────────────────────────────────┐
│ STAGE 4: TOOL EXECUTION (with validation & timeout)          │
│ - Validate input against Zod schema (if defined)            │
│ - Execute tool handler with context                          │
│ - Timeout: 30 seconds (heavy planning)                       │
│ - Record tool usage metadata                                 │
│ - On failure: return explicit error (NEVER free chat)       │
└──────────────────┬───────────────────────────────────────────┘
                   ▼
┌─────────────────────────────────────────────────────────────┐
│ STAGE 5: RESPONSE BUILDING                                   │
│ - Build structured response with data                        │
│ - Include: text, structuredData, toolsUsed, citations       │
│ - Return ChatAgentResponse                                   │
└─────────────────────────────────────────────────────────────┘

CONTROLLED FALLBACK PATH (General Intent Only):
If intent = "general" AND no tool is registered:
1. Build conversational prompt with history
2. Generate LLM response (timeout: 30s)
3. Return text response with metadata

BLOCKED PATH (Operational Intents):
If intent ∈ {cg, lineup, shifts, news, rights}:
- Free chat is FORBIDDEN
- Must execute tool OR ask clarification OR return error
- Safety net: if somehow reached, returns explicit error

ERROR HANDLING:
- LLM timeout → "הבקשה לקחה יותר מדי זמן"
- Tool timeout → "הפעולה לקחה יותר מדי זמן"
- Tool failure → Return tool.error message
- Unexpected error → "אירעה שגיאה בעיבוד הבקשה"

TIMEOUT STRATEGY:
Function: withTimeout<T>(promise, ms, label)
- Uses Promise.race with setTimeout
- Does NOT use AbortSignal (Node 18 compatibility)
- Clears timer on completion
- Logs timeout events with trace ID

9. INTENT CLASSIFICATION & ROUTING
================================================================================

INTENT CLASSIFIER:
File: services/ai-agent/src/agent/intent-classifier.ts

SUPPORTED INTENTS:
1. lineup - Program rundowns, segments, show planning
2. cg - Graphics requests, lower thirds, scorebugs, tickers
3. shifts - Shift scheduling, work assignments, availability
4. news - News briefs, breaking news, current events
5. rights - Broadcast rights, sports fixtures, league info
6. general - General questions, greetings, help requests
7. clarification - Message unclear, need more information

CLASSIFICATION METHODS:

1. Quick Classify (Pattern Matching):
   - Fast keyword-based classification
   - Used before LLM for common patterns
   - Example: "חדשות" → news, "גרפיקה" → cg
   
2. LLM Classification:
   - Uses INTENT_CLASSIFICATION_PROMPT
   - Returns JSON with intent, confidence, entities
   - Example response:
     {
       "intent": "lineup",
       "confidence": 0.85,
       "entities": { "showType": "sports", "date": "tonight" },
       "reasoning": "User wants to build a sports rundown"
     }

ENTITY EXTRACTION:
Extracts relevant data from messages:
- Dates and times (tonight, tomorrow, specific dates)
- Names (people, teams, shows)
- Types (sports, news, entertainment)
- Numbers (durations, counts)
- Locations (venues, cities)

CLARIFICATION LOGIC:
Function: needsClarification(intent)
Returns true if:
- confidence < 0.6
- intent = "clarification"
- critical entities missing

Function: generateClarificationRequest(intent, message)
Builds contextual questions:
- "מה סוג התוכנית שאתה רוצה לבנות?" (for lineup)
- "איזה סוג גרפיקה אתה צריך?" (for CG)
- "על איזה תקופה אתה מדבר?" (for shifts)

GREETING DETECTION:
Function: isGreetingMessage(message)
Patterns:
- Hebrew: "שלום", "היי", "מה קורה", "מה המצב"
- English: "hi", "hello", "hey", "what's up"
- Case insensitive, trimmed

Function: getGreetingResponse(message)
Returns localized greeting:
- Hebrew input → "היי! אני לנסלוט. איך אוכל לעזור?"
- English input → "Hi! I'm Lancelot. How can I help?"

15. SECURITY & E2EE SUPPORT
================================================================================

END-TO-END ENCRYPTION:
The AI agent supports E2EE as a first-class crypto participant.

E2EE DESIGN DOCUMENT:
File: Prompts/Security Prompt.txt (183 lines)

KEY PRINCIPLES:
- Messages encrypted on sender's client
- Decrypted only on recipient's client (or AI agent service)
- Server/database never see plaintext
- AI agent owns cryptographic keys

CRYPTOGRAPHIC APPROACH:
- Key Exchange: X25519 (Diffie-Hellman)
- Message Encryption: ChaCha20-Poly1305
- Identity Keys: Long-term per-user keys
- Session Keys: Per-conversation keys

AI AGENT CRYPTO IMPLEMENTATION:
Directory: services/ai-agent/src/crypto/

e2ee.ts:
Functions:
- generateKeyPair(): Generate X25519 keypair
- encryptMessage(plaintext, recipientPublicKey): Encrypt message
- decryptMessage(ciphertext, senderPublicKey): Decrypt message
- computeFingerprint(publicKey): SHA-256 fingerprint

keyManager.ts:
Functions:
- initializeKeys(): Load or generate AI agent keys
- getPublicKey(): Get AI agent public key
- getPrivateKey(): Access private key securely
- storeKeys(): Persist keys (encrypted at rest)

KEY STORAGE:
- Private key encrypted with env-based passphrase
- Stored in MongoDB or filesystem (configurable)
- Never logged or transmitted

MESSAGE FLOW (E2EE):
1. User encrypts message with AI agent's public key
2. Sends encrypted blob via Socket.IO
3. API Gateway routes to AI agent
4. AI agent decrypts using private key
5. Processes plaintext internally
6. Encrypts response with user's public key
7. Returns encrypted blob
8. API Gateway forwards to user
9. User decrypts locally

FEATURE FLAG:
Environment: ENABLE_E2EE_CHAT=true
Config: config.features.enableE2eeChat

When disabled:
- E2EE messages rejected with error
- Falls back to plaintext mode
- User warned if E2EE requested

SECURITY CONSTRAINTS:
- AI agent never logs decrypted message content
- Only logs hashes/message IDs for observability
- Explicitly wipes decrypted buffers after use
- Tool outputs encrypted before sending

KEY FINGERPRINTS:
- SHA-256 hash of public key
- Displayed to users for verification
- Detected if key changes (MITM protection)
- Stored per user in database

BACKWARD COMPATIBILITY:
- Supports both plaintext and E2EE chats
- Automatic negotiation based on recipient capabilities
- Feature flag controls rollout
- Graceful fallback with user warnings

- Multiple Ollama instances (load balancing)

NEW HELPER FUNCTIONS (All additive, no breaking changes):

ORCHESTRATOR (orchestrator.ts):
- isOperationalIntent(intent: string): boolean
  → Returns true for cg/lineup/shifts/news/rights

  → Returns short Hebrew clarification for missing entities

INTENT CLASSIFIER (intent-classifier.ts):
- detectLineupType(message): 'items' | 'structure' | undefined
  → Detects whether user wants content items list or segment structure
  
- extractItemCount(message): number | undefined
  → Extracts "12 פריטים" → 12
  
- extractCategoryCounts(message): Record<string, number> | undefined
  → Extracts "5 כדורגל ישראלי, 3 ספורט אחר" → { "כדורגל ישראלי": 5, ... }

LINEUP BUILDER (lineup-builder.ts):
- generateItemsLineup(request & { totalItems, categoryCounts }): Promise<ItemsLineup>
  → Fetches real articles from RSS, assigns to categories with relevance scoring
  → Returns exactly N items with exact category distribution
  → Real articles get source citations; unfilled slots = placeholders
  
- fetchAndAssignArticles(categoryRequests): Promise<Record<string, CachedArticle[]>>
  → Global article pool → score per category → assign (no duplicates)
  
- scoreArticleForCategory(article, rules, category): number
  → Scores article relevance: mustMatch, boostMatch, excludeMatch filters

CG SPEC GENERATOR (cg-spec-generator.ts):
- parseLiveCGMessage(message): LiveCGParseResult
  → Deterministic regex extraction of teams/scores/times/names
  → Returns: { parseSuccess, templateType, fields, missing, validationErrors }
  → NEVER guesses; missing data explicitly listed
  
- isLiveCGRequest(message, mode): boolean
  → Detects LIVE_CG mode from context or message prefix

VALIDATION UTILS (validation.ts):
- validateCGTextField(value, maxLen): { valid, error? }
  → Validates against Viz broadcast constraints (length, control chars)
  
- normalizeRTL(text): string
  → Strips bidi control chars, collapses whitespace, trims
  
- enforceStructuredOutput<T>(rawOutput, schema, repairFn): Promise<ValidationResult<T>>
  → Zod validation + single repair attempt → explicit error if still invalid

SHIFT SOLVER (shift-solver.ts):
- extractShiftConstraints(message): ExtractedConstraints
  → Extracts department, week, roles, hard constraints from natural language
  → Returns: { department?, weekStartDate?, roles, hardConstraints, availabilityNotes, missingConstraints }
  → NEVER produces a schedule (constraints only)
