Shifts module assessment (Shifts Admin Dashboard + User Shifts)

Admin Dashboard (apps/web/src/components/shifts/admin/ShiftsAdminDashboard.tsx)
- Functional bugs
  - [x] Uses s.role for filtering day shifts by role (lines ~1094-1109), but GET_SHIFTS_BY_WEEK query does not return a role field on the shift object; role exists per assignedWorker. Filtering is ineffective/incorrect.
  - [x] AssignmentSettingsModal save drops form values; handleSave only sends departmentId/name and omits assignmentSettings, plus hard-codes 'IT' fallback for IDs. Settings are not persisted.
  - [x] Non-department admins/system admins: departments array resolves to empty []; no UI to pick a department; schedule grid likely renders nothing. (Derived departments from data for system admins.)
  - [x] Create/assign workflow ignores requiredStaff from configuration; hard-codes requiredWorkers: 1 when creating a shift.
  - [x] No validation against availability constraints or capacity when assigning; allows over-assignment; only prevents duplicate assignment of the same user to the same shift.

- Data/schema mismatches
  - Inline GraphQL operations are defined inside the component (shifts, templates, requests, employees, special days, notifications, reports) instead of centralized in apps/web/src/graphql; duplicates/mismatch risk with backend schema.
  - Uses users { id, displayName, department, email } query without pagination/filters; heavy and may not match server schema used elsewhere (e.g., GET_EMPLOYEES_BY_DEPARTMENT shape differs).

- Date/time libraries & week logic
  - Mixed usage of moment and dayjs in the same component; increases bundle size and risks inconsistent parsing/formatting.
  - Week handling uses moment().startOf('week'), while other parts of the app (AvailabilityConstraints) rely on dayjs with isoWeek plugin; potential off-by-one-week or start-day mismatch.

-- UX/UI issues
  - [x] Labels/text mismatched in Hebrew:
    - [x] Constraints UI: minRestBetweenShifts mislabeled; maxNightShiftsPerWeek mislabeled.
  - Shift templates list switch uses defaultChecked with no onChange handler; toggling does nothing.
  - Department roles managed locally via localStorage (per-browser, not persisted server-side); creates inconsistent experience across admins/devices and is easy to lose.
  - Large, complex single file (~2.5k lines) with many concerns (calendar, employees, roles, notifications, special days, reports, multiple modals) — difficult to maintain and test.
  - Many Ant icons/components imported; likely increases bundle size unnecessarily.
  - Contact section contains hard-coded phone/email (no environment/i18n), and appears unrelated to shifts admin scope.

-- Performance & data loading
  - [x] Fires five concurrent GET_SHIFTS_BY_WEEK queries for nearby weeks; unnecessary load without caching/pagination; no error UI for failed week loads.
  - users/employees queries unpaginated; can be large.

-- Permissions/integration
  - [x] Admin gating uses user.systemRole inside the component, but the page uses user.permissions; inconsistent gate logic may show admin tile but block features (or vice versa).
  - Client enforces little; relies on backend to reject invalid assignments; no optimistic/pessimistic guards.

- i18n/accessibility
  - Extensive hard-coded Hebrew strings without next-i18next usage; inconsistent with i18n strategy elsewhere.
  - Drag-and-drop on buttons without ARIA; color-only availability cues reduce accessibility.

User Shifts: AvailabilityConstraints (apps/web/src/components/shifts/AvailabilityConstraints.tsx)
- Functional/logic
  - [x] SHIFT_TYPES are hard-coded (morning/afternoon/night) rather than derived from department configuration; breaks if departments define custom shiftTypes/roles.
  - startOf('week') used with dayjs (isoWeek plugin loaded but not used); may not align with admin view (moment) or local expectations; potential mismatch in weekStartDate sent to server.
  - [x] On week navigation, unsaved changes are cleared without a confirmation prompt.
  - Added graceful derivation of shift types from department config.

- UX/i18n
  - All strings hard-coded; no i18n usage.
  - Green “available” default paints the entire grid as green, which can be visually noisy; could use neutral default.

User Shifts: ShiftSwap (apps/web/src/components/shifts/ShiftSwap.tsx)
- Functional/logic
  - [x] USERS_QUERY fetches all users without pagination or department filtering; allows selecting any user, including outside the department; likely policy violation.
  - [x] No prevention from selecting self as targetUser.
  - Lacks validations (e.g., only shifts the user is assigned to should be swappable; not enforced client-side).

- Data/schema
  - Unpaginated users fetch; potential performance issues on large datasets.

- UX/i18n
  - Hard-coded strings; no i18n usage.
  - Swap requests table doesn’t offer cancel/withdraw action; limited lifecycle management.

User Shifts: UpcomingShifts (apps/web/src/components/shifts/UpcomingShifts.tsx)
- Functional/logic
  - [x] Displays static time ranges per shiftType map instead of actual startTime/endTime from server; may mislead when shifts deviate from defaults.
  - [x] Polls every 60s without a quick manual refresh or pause; acceptable but could be wasteful. (Added manual refresh link.)

- UX/i18n
  - Hard-coded Hebrew strings; no i18n usage.

User Shifts: VacationRequest (apps/web/src/components/shifts/VacationRequest.tsx)
- Functional/logic
  - [partial] Basic overlap guard scaffolding added; consider full validation against policy rules on backend.
  - Minimal validation; does not enforce max duration, blackout periods, or department policies.

- UX/i18n
  - Hard-coded strings; no i18n usage.

Shifts Page (apps/web/src/app/shifts/page.tsx)
- Admin gating inconsistent with Admin Dashboard’s internal checks (permissions vs systemRole); can expose admin tile but fail inside, or hide admin tile while systemRole would allow.
- Eagerly imports admin dashboard even for non-admins (no code splitting); unnecessary bundle weight.

Cross-cutting (module-wide)
- Mixed date libraries (moment + dayjs) and inconsistent week semantics (startOf('week') vs isoWeek) risk alignment issues between admin and user views and with server weekStart expectations.
- GraphQL operations duplicated and scattered; not using generated types; increases schema drift risk and runtime errors.
- No central permission system usage for client gating (ties into broader app issue of duplicate permission systems).
- Heavy components, minimal error boundaries, and lack of pagination/caching strategies may hurt performance and resilience.
